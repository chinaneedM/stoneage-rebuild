# StoneAge persistent battle state and first termination boundary — R1

Date: 2026-09-20

Status: **stable-descendant FACT for the observed server behavior; reconstruction-safe in-process state model; JSS-era byte-level server provenance remains OPEN**

## Purpose

This closes the first persistent multi-round battle-state seam after the
ordinary attack / guard / wait resolver.

The reconstruction can now retain battle HP across rounds, advance a turn
counter, remember the last submitted command set and stop accepting new rounds
once the battle enters a terminal state.

Rewards and post-battle settlement remain deliberately separate.

## 1. End checks happen after a completed battle round

The stable loop performs the battle action pass first:

```
pBattle->turn++;
BATTLE_ai_all(...);
BATTLE_Battling(...);
```

and then tests both sides for battle continuation.

The reconstruction therefore updates all HP generated by one deterministic
ordinary round before evaluating termination.

## 2. BATTLE_OnlyRescue() does not count pets as side-survival actors

The stable `BATTLE_OnlyRescue()` loop explicitly contains:

```
if (CHAR_getInt(charaindex, CHAR_WHICHTYPE) == CHAR_TYPEPET)
    continue;
```

before it checks whether the actor is alive.

It then counts living non-pet characters.

For the current single-player subset this has an important consequence:

- player side: the human player is the survival-bearing actor;
- allied pets do **not** keep the side alive by themselves;
- enemy side: ordinary enemy actors count as non-pet survival-bearing actors.

Therefore, if the player reaches zero HP while an allied pet still has HP,
the current historical battle side is nevertheless finished.

This behavior is intentionally preserved rather than replaced with a modern
"any party unit alive means battle continues" rule.

## 3. Side-check order is asymmetric and preserved

The stable source checks side 0 first:

```
if (BATTLE_OnlyRescue(battleindex, 0, ...) == 0) {
    winside = 1;
    finish = TRUE;
} else if (BATTLE_OnlyRescue(battleindex, 1, ...) == 0) {
    winside = 0;
    finish = TRUE;
}
```

R1 preserves this order.

In the degenerate case where both sides have zero eligible survival-bearing
actors at the same check point, side 1 is therefore selected as winner by the
stable branch order rather than inventing a draw.

The current ordinary sequential attack seam normally does not create that
condition, but the rule is recorded now so later simultaneous/reaction systems
do not silently change it.

## 4. Rescue-mode nuance remains outside R1

`BATTLE_OnlyRescue()` also tracks whether the only surviving non-pet actors
are in `BATTLE_CHARMODE_RESCUE`.

The current single-player battle model does not yet implement rescue/join
battle modes, so R1 uses only the stable non-pet survival count.

No rescue behavior is guessed or flattened into ordinary single-player
combat.

## 5. Persistent battle state

Implementation:

- `tools/stoneage_battle_state_model.py`

The state stores:

- immutable original `BattleSession`;
- stable battle-slot mapping;
- current HP by participant id;
- completed turn count;
- `active` / `finished` phase;
- `victory` / `defeat` result when finished;
- winning side 0 / 1;
- previous round's submitted command mapping.

Static combat properties stay on `BattleParticipant`; changing battle HP is
kept in the persistent state rather than mutating the original session.

This keeps recovered master/runtime identity separate from transient battle
effects.

## 6. Only living actors need commands on following rounds

A participant that was killed in a prior round remains in the battle state
for identity/history, but it is not re-submitted to the next action-order
preparation.

The next round therefore requires commands and initiative random results for
exactly the currently living actors.

Execution-time target retargeting still sees a previously dead target slot as
invalid and applies the already recovered random opponent retarget rule.

## 7. Runtime integration

`tools/stoneage_singleplayer_runtime.py` now exposes:

- `start_persistent_battle_state()`
- `resolve_persistent_battle_round()`

The engine-facing chain can therefore execute:

```
BattleSession
 -> persistent battle state
 -> round 1
 -> updated HP / turn 1
 -> round 2
 -> ...
 -> finished + winning side
```

without network/server processes and without the caller manually carrying
intermediate HP.

## 8. Minimal terminal HP settlement is now closed separately

The termination model itself still does not infer rewards. A later
reconstruction adapter now consumes only an already-finished
`PersistentBattleState` and projects its direct HP/result state back into the
single-player persistent domain.

Canonical settlement record:

- `research/mechanics/STONEAGE-BATTLE-SETTLEMENT-R1.md`

The closed R1 projection is deliberately limited to:

- `victory` / `defeat` result;
- terminal player HP;
- terminal HP of allied pets that participated;
- unchanged battle-origin world position.

It still does **not** imply:

- EXP award or level-up;
- drops;
- money;
- capture result;
- escape result;
- death penalties;
- healing/revival;
- post-battle warp;
- equipment durability;
- any later extension settlement.

Those remain later independently recovered seams.
